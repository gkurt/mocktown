# Spike 02 — oRPC on Bun

**Status:** Complete · **Date:** 2026-08-31 · Bun 1.4.0, oRPC 1.15.0, Zod 4.5.4

## The question

[02-architecture.md](../../docs/design/02-architecture.md) chose oRPC with Zod v4 contracts
— "one procedure definition, three surfaces" — and left two things to this spike:

> served by oRPC's OpenAPIHandler directly on `Bun.serve` … the MCP server (phase 2) is
> generated by walking the contract … (evaluate existing adapters like trpc-cli/oRPC-MCP at
> spike time; worst case the walk is a couple hundred lines we own).

## Verdict

**The decision holds unchanged, and the walk costs 161 lines, not "a couple hundred".**

Everything passes on Bun with no patches, no framework, and no runtime surprises —
a marked contrast with [spike 01](../01-mockttp-bun/FINDINGS.md).

| | |
|---|:--:|
| `OpenAPIHandler` on `Bun.serve`, GET with query params | PASS |
| PUT with a path parameter and a JSON body | PASS |
| Contract validation rejects bad input (400 from the same Zod schema) | PASS |
| Static GUI files from the same `Bun.serve`, no framework | PASS |
| Per-session bearer token enforced on `/api` | PASS |
| OpenAPI document generated from the contract | PASS |
| Typed oRPC client round-trip | PASS |
| Contract walk enumerates every procedure | PASS |
| CLI generated from the contract (spawned as a real process) | PASS |
| MCP server generated from the same walk | PASS |
| | **10/10** |

Reproduce: `bun run spike.ts`. Type safety: `bunx tsc --noEmit`.

## Build our own walk — don't take an adapter

The doc asked us to evaluate existing adapters. Both were rejected, on evidence:

| Candidate | Verdict |
|---|---|
| `orpc-mcp` @ 0.1.3 | **No.** 329 downloads/week, four releases, single maintainer, 0.x. This is the surface agents drive Mocktown through; a dependency this early is a larger risk than 38 lines of our own. |
| `trpc-cli` @ 0.16.0 | **No.** Popular (232k/week) but it is a tRPC adapter — its description and keywords are tRPC-only, and oRPC is a different contract shape. Wrong tool. |

`walk.ts` (44 lines) is the whole traversal; `cli.ts` (79) and `mcp.ts` (38) consume it.
**161 lines total**, comfortably inside the budget, and it buys three things an adapter
wouldn't:

- **One coupling point.** oRPC hangs the contract definition off a `~orpc` property. That
  is touched in exactly one function (`procedureDef`); if oRPC moves it, one function
  changes and both generators are untouched.
- **House rules are ours to set.** `readOnlyHint` on MCP tools is derived from the HTTP
  method — GET procedures are safe for an agent to call speculatively, PUT/POST are not.
  That mapping is a Mocktown policy decision, not something to inherit from a dependency.
- **The CLI output contract is enforceable.** `--json` on every command and "the resolved
  project on the first line" ([08-projects-config.md](../../docs/design/08-projects-config.md))
  are structural properties of the generator, so no future command can quietly break them.

## What the contract actually buys

- **Add a procedure, get three surfaces.** A new entry in `contract.ts` produces an HTTP
  route, an OpenAPI operation, a CLI command with flags and help text, and an MCP tool with
  a JSON-Schema input — no other file edited.
- **Validation cannot drift.** The 400 on a bad `provider` and the CLI's refusal to send it
  come from the same `ProviderRef` schema.
- **The types have teeth.** `type-safety-check.ts` holds four deliberate mistakes — a
  missing required input, an unknown input field, and two handlers returning the wrong
  shape — each marked `@ts-expect-error`. `tsc` is silent, meaning all four do error. The
  check was itself verified by adding a directive to a *valid* call and confirming tsc
  reports it as unused, so a silent pass can't be mistaken for working types.
- **OpenAPI comes out right without hand-holding.** Path params are extracted into
  `parameters`, the remaining fields land in `requestBody`, and `.describe()` text on the
  Zod fields becomes the documentation agents read.

## Notes for the implementation

1. **`@orpc/openapi-client/fetch`'s `OpenAPILink` is the client for all three surfaces.**
   The CLI and MCP server are both just clients of the daemon — neither imports the router.
   That keeps 02-architecture.md's "no client has privileged access to anything" structural
   rather than aspirational.
2. **The OpenAPI document is served unauthenticated**, everything under `/api` is not. The
   spec is documentation and contains no project data; requiring a token to read it would
   only make life harder for agents and `curl`.
3. **`Bun.serve` binds `127.0.0.1` explicitly** rather than relying on the default
   ([10-security.md](../../docs/design/10-security.md)).
4. **MCP tool names flatten the contract path with `_`** (`services.list` → `services_list`),
   since MCP tool names can't carry dots.
5. **CLI flags cover top-level input fields only.** Nested objects (seed editors, scrub-rule
   config) will need either a `--field.sub` convention or a file argument. Not needed for
   phase 1's commands; decide when the first nested input appears.

## Not tested here

- `@orpc/tanstack-query` in a real React GUI (phase 4). The package exists at the matching
  version; the GUI is not built yet.
- Server-sent events / streaming procedures (the live feed in phase 4 will want them).
- Performance under load. The daemon is a local single-user service, so this is unlikely
  ever to matter, but nothing here measured it.
